# 午後過去問を解くための小刻みな学習

## 目的

原問の各設問に必要な知識、条件の読取り、因果関係、答案の組立てを学ぶ。
共通の基礎章を大量につなぎ、原問を小問に分けただけでは完成ではない。
初めは原問を読まなくても、タップだけで学べる。原文・図は後半に必要な範囲だけ示す。
最後の原問全体への解答は、既存の原問画面で別に保存する。

## ファイル

`src/content/workshops/{examId}-{pm1|pm2}-q{n}.json` に記述する。

```json
{
  "examKey": "2025r07h/pm2/2",
  "title": "遠隔検針を小さな通信から設計する",
  "verifiedSources": ["https://www.ipa.go.jp/公式問題PDF"],
  "sections": [
    {
      "id": "power",
      "title": "電池で動かす機器の条件",
      "targets": ["s1", "s4-2"],
      "steps": []
    }
  ]
}
```

`targets` は `originals.json` の小問ID。全ての有効な小問を少なくとも一節で扱う。
単にtargetsへ列挙するだけではなく、その小問の全回答要素を練習で扱う。
不成立として除外された設問は含めない。
`steps` は既存の `info / quiz / blank / parsons` スキーマを使用する。
各ステップは `id,type,title,format,theme,scaffold,stage` が必要。
`stage` は `concept / check / apply / reason / assemble / transfer` のいずれか。
穴埋めのキーは英字で始まる英数字・ハイフン・アンダースコアとし、`{area}` のように文中に記載する。
全キーと空欄定義を一致させ、同じステップ内に重複するキーを定義しない。
idは節内一意。既存回答を保つため公開後に別の問題に再利用しない。
初期段階で `original / write / calc` や原問全文の読解を要求しない。
計算も、条件の選択→式の選択→計算結果の選択に分ければタップで実施できる。

## 一節の設計

1. 何を実現したいか、何が困るかを2〜4文で説明する。
2. 用語・役割を1つずつ確かめる。略語は初出で正式名称を示す。
3. 完結した小さな条件を設問内に与え、1つの判断を選ばせる。
4. なぜその判断になるかを問う。紛らわしい誤答にも固有の解説を付ける。
5. 穴埋めや並べ替えで、条件→動作→結果の答案を組み立てる。
6. 少し条件を変えた問題、または原問の最小限の抜粋で確かめる。

1節4〜10ステップ程度。大問全体で40〜100程度を目安とし、分量より理解の連続性を優先する。
少なくともquiz、blank、parsonsの3形式を使う。
節ごとに原問へどうつながるか説明する。答えを丸暗記させる選択肢にしない。
複数の空欄・複数指定がある小問は、必要な要素を落とさない。
暗号化と閉域、IPとMAC、ACKとアプリケーション応答等の混同を誤答で扱う。

## 原典・図

- `data/original-index/{examId}_nw_{division}_qs.json` に原画像のOCR位置情報がある。
- スキャンPDFはpdftotextでは空になるので、その場合は索引のtextと原画像を併用する。
- `src/content/originals.json` に大問ページ範囲、公式解答例、小問IDがある。
- 本文・設問・図の位置関係を原画像で確認する。OCR誤読をそのまま教材にしない。
- 公式PDFを実際に確認したURLを `verifiedSources` に記録する。
- 技術的に不明な点はRFC・ベンダー公式資料等の一次資料で確認する。
- 自作の図は既存fig DSLを使い、説明用と明記する。原問の図の代用品にしない。
- 構成は機器アイコン付き`topo`、電文は`header / encap`、出力例は`console`を使う。表やフローだけで構成・パケットのイメージを代替しない。
- 原画像の一部を示す場合、stepに以下の任意プロパティを使える。

```json
"originalExcerpt": {
  "page": 20, "top": 0.05, "bottom": 0.6,
  "label": "図5の要求と応答（IPA原図）"
}
```

pageは問題冊子のPDFページ番号。top/bottomは0〜1の画像上端からの比率。
抜粋だけで条件が不足する場合は、問題内に条件を自分の言葉で短く補足する。
補足は引用・原文ではなく「練習用の条件」として明示する。
原問が特定の実装・仮定を置く場合、一般仕様と混同しないよう限定する。

## 検証

`npm run validate` で参照小問・基本構造を確認する。
機械検証だけでは教育上の品質は保証できない。原問の全要素と対応させて人手で読み直す。
本文の読み方・条件・誤答の理由が欠けた箇所は、完成と報告しない。
